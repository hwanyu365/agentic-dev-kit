# /add:tdd

## 0. 전제

- `CLAUDE.md` 에 `## 자율 범위` 절이 없으면 ADD 저장소가 아니다. 이 스킬을 진행하지 않고 알린다.

## Red

- 대상 TC 를 스펙 §7 에서 읽고, CLAUDE.md 성숙도 표의 TDD 행으로 자동화할 TC 를 고른다 (`poc` 선택, `alpha` 핵심 로직, `beta` 이상 전체).
  - 자동화하지 않는 TC 와 비고에 실기기·다른 저장소 담당이 적힌 TC 는 Red 를 만들지 않는다. 목록으로 보고하고 `/add:verify` 에서 확인 방법을 적는다.
- 테스트 위치·이름 규칙은 `CLAUDE.md` 를 따른다 (이름은 `TC#n` 으로 시작).
- 테스트 이름과 내용은 지금 고정하는 동작을 적는다. 이슈 번호나 "~하던 문제" 같은 이력은 쓰지 않는다.
- 검증 명령의 테스트 부분을 실행해 **새 테스트가 기대한 이유로 실패하는 출력**을 확인한다.
  - 컴파일 오류만으로 실패하면 Red 가 아니다. 최소한의 시그니처를 만들어 단언에서 실패하게 한다.
  - 구현 전에 통과하면 테스트가 새 동작을 검증하지 않는 것이다. 테스트를 고친다.
- 이번 Red 에서 만든 테스트 목록(파일·이름)을 기록해 둔다. Green 이후 대조에 쓴다.

## Green

- 테스트를 통과시키는 최소 구현만 한다. 스펙에 없는 기능을 덧붙이지 않는다.
- 같은 입력을 읽거나 같은 산출물을 만드는 다른 경로를 세고, 이번 변경이 닿아야 하는 곳을 빠뜨리지 않는다.
- Red 테스트를 지우거나 단언을 약화하지 않는다. 테스트가 틀렸다고 판단되면 멈추고 근거와 함께 저장소 소유자에게 묻는다.
- 같은 TC 를 통과시키려는 수정이 3번 실패하면 멈추고 보고한다 → 추측으로 고치기를 이어 가지 않고 스펙·설계의 가정을 다시 본다.

## Refactor

- 동작을 바꾸지 않고 정리한다. 매 단계 테스트를 다시 돌린다.
- 주석은 기본적으로 쓰지 않는다. 코드로 드러나지 않는 이유만 남긴다.

## 끝

- 검증 명령 전체를 실행해 출력으로 통과를 확인한다.
- Red 에서 기록한 테스트가 모두 남아 있고 통과하는지 대조한다.
- 보안 경계(권한 규칙·인증 검사)를 바꿨으면 조건마다 지워도 실패하는 TC 가 있게 만든다. 확인 절차와 기록 형식은 `/add:verify` 2-2 를 따른다.
