# /add:verify

테스트 통과는 완료 근거가 아니다. 그 테스트가 스펙에서 나왔는지, 스펙 항목이 빠짐없이 구현됐는지를 함께 본다.

## 1. 검증 명령

- `CLAUDE.md` "검증" 의 명령을 실행하고 요약 출력을 보여 준다. 실패하면 여기서 멈춘다.

## 2. 스펙 전수 대조

- 대상: 인자로 받은 기능 스펙, 없으면 이번 브랜치에서 바뀐 스펙 파일 (`git diff --name-only origin/main...HEAD -- docs/`)
- §3·§4·§6 항목마다 표를 만든다.

  | 항목 | 구현 위치 | 검증 TC | TC 테스트 위치 |
  | --- | --- | --- | --- |

  - 구현 위치는 grep 결과가 아니라 실제로 읽어서 확인한 함수·파일이다. 호출 체인을 따라가 동작하는 경로인지 본다.
  - TC 는 `git grep -n "TC#n"` 으로 테스트 코드에서 찾는다. 스펙에만 있고 코드에 없으면 미구현이다.
  - 비고에 다른 저장소·실기기 담당이 적힌 TC 는 그 사실을 표에 남긴다.
- 빈 칸이 하나라도 있으면 미완료다. 덩어리 단위("A 기능 완료")로 뭉치지 않는다.

## 3. 변경 범위

- 이번 diff 가 바꾼 입력·출력·설정마다 그것을 읽거나 만드는 다른 경로를 센다.
- 고치지 않은 경로는 왜 영향이 없는지 한 줄로 적는다.
- 분기·기본값·에러 경로를 지웠다면 그것이 막고 있던 실패가 조용한 통과로 바뀌지 않았는지 확인한다.

## 4. 보고

- 판정: 완료 / 미완료(빈 칸 목록)
- 실행한 명령과 결과, 실행하지 못한 것(실기기, 다른 저장소)을 구분해 적는다.
- 대조 표는 PR 본문이나 세션 보고에만 쓰고 스펙 문서에는 남기지 않는다.
