# /add:verify

테스트 통과는 완료 근거가 아니다. 그 테스트가 스펙에서 나왔는지, 스펙 항목이 빠짐없이 구현됐는지를 함께 본다.

## 0. 전제

- `CLAUDE.md` 에 `## 자율 범위` 절이 없으면 ADD 저장소가 아니다. 이 스킬을 진행하지 않고 알린다.
- chore 이슈면 1·3·4 만 한다.

## 1. 검증 명령

- `sh .claude/hooks/verify.sh` 를 실행하고 요약 출력을 보여 준다. 실패하면 여기서 멈춘다.
  - CI 와 같은 추적성 검사(`.github/spec-trace.sh`)와 `CLAUDE.md` "검증" 의 명령을 돌리고, 통과한 작업 트리를 기록한다 → 그 뒤에 파일을 고치면 커밋 직전 hook 이 막는다.
- CI 의 비밀 파일 가드를 아직 추적하지 않은 파일까지 넓혀 돌린다 → 로컬 통과가 CI 통과를 뜻하게 한다.
  - `git -c core.quotePath=false ls-files --cached --others --exclude-standard | grep -Ef .github/secret-files.regex | grep -vE '\.example$'` 결과 0건

## 2. 스펙 전수 대조

- 대상: 인자로 받은 기능 스펙, 없으면 커밋 전 변경까지 포함해 바뀐 스펙 파일
  - `git diff --name-only $(git merge-base origin/main HEAD) -- docs/` 와 `git ls-files --others --exclude-standard docs/`
- 표(2, 2-1)는 대화 이력 없는 읽기 전용 subagent 에게 맡긴다 → 구현한 맥락을 모르는 쪽이 채워야 자기 코드를 근거로 넘어가지 않는다.
  - 대상 스펙 파일, 2·2-1 의 규칙, 2-1 의 diff 범위, 성숙도, 1의 추적성 검사 출력을 전달하고 스타일은 보지 말라고 한다.
  - 추적성 검사는 ID·TC·테스트 이름이 있는지만 본다. 구현 위치가 동작하는 경로인지, 테스트가 그 계약을 검증하는지는 이 표가 맡는다.
  - 돌아온 표의 빈 칸과 "구현됨" 판정 중 근거가 약한 것은 직접 읽어 확인한다.
- §3·§4·§6 항목마다 표를 만든다.

  | 항목 | 구현 위치 | 검증 TC | TC 테스트 위치 | Then 단언 |
  | --- | --- | --- | --- | --- |

  - 구현 위치는 grep 결과가 아니라 실제로 읽어서 확인한 함수·파일이다. 호출 체인을 따라가 동작하는 경로인지 본다.
  - TC 는 `git grep -n -w --untracked "TC#n"` 으로 테스트 코드에서 찾는다. 스펙에만 있고 코드에 없으면 미구현이다.
    - `-w` 가 없으면 `TC#1` 이 `TC#10` 에 맞고, `--untracked` 가 없으면 아직 커밋하지 않은 테스트를 못 찾는다.
  - Then 단언: TC 테스트가 스펙의 When 을 실행하고 Then 의 관측 결과를 단언하는지 읽어서 적는다. 이름만 TC 이고 다른 것을 확인하면 빈 칸이다.
  - §6 항목은 그 결정이 근거가 된 요구사항의 TC 로 대조한다.
  - 성숙도가 자동화를 요구하지 않는 TC 는 TC 테스트 위치 칸에 `수동: {확인 방법과 결과}` 를 적는다. 확인하지 않았으면 빈 칸이다.
  - 비고에 다른 저장소·실기기 담당이 적힌 TC 는 그 사실을 표에 남긴다.
- 빈 칸이 하나라도 있으면 미완료다. 덩어리 단위("A 기능 완료")로 뭉치지 않는다.

## 2-1. 역대조 (코드 → 스펙)

- 2는 스펙에 있는 것이 구현됐는지만 본다. 스펙에 없는 동작이 들어온 것은 반대 방향으로 센다.
- 이번 diff(`git diff $(git merge-base origin/main HEAD)` + 미추적 파일)가 새로 만든 분기, 권한·검증 조건, 사용자에게 보이는 문구, 설정 값마다 한 행을 만든다.

  | diff 위치 | 무엇 | 근거 ID |
  | --- | --- | --- |

- 근거 ID 가 없으면 스펙 누락이다 → `/add:spec`. 동작이 같은 정리(리팩터링)면 근거 ID 칸에 `동작 동일: {이유}` 를 적는다.

## 2-2. 보안 경계 mutation (해당 시)

- 실제 보안 경계(권한 규칙·인증 검사)의 조건마다 한 행을 만든다. 일부 조건만 지워 보지 않는다.

  | 조건 (파일:라인) | 지운 방법 | 실패한 TC |
  | --- | --- | --- |

- 세션이 직접 한다. 커밋 전이라 `git diff` 로는 되돌렸는지 알 수 없으므로 검증 래퍼의 기록과 비교한다.
  - 시작 전 `sh .claude/hooks/verify.sh` 로 통과 기록을 남긴다.
  - 조건 하나를 지우고 `CLAUDE.md` "검증" 의 명령(래퍼가 아닌 원래 명령)을 돌린 뒤 되돌린다 → 래퍼는 시작할 때 기록을 지운다.
  - 끝나면 `sh .claude/hooks/verify.sh --check` 가 통과해야 한다 → 미추적 파일까지 mutation 전과 같다.
- 지워도 실패하는 TC 가 없으면 빈 칸 → 미완료다 (`/add:tdd` 로 TC 추가).
- 표는 PR 본문 "검증" 에 그대로 쓴다.

## 3. 변경 범위

- 이번 diff 가 바꾼 입력·출력·설정마다 그것을 읽거나 만드는 다른 경로를 센다.
- 고치지 않은 경로는 왜 영향이 없는지 한 줄로 적는다.
- 분기·기본값·에러 경로를 지웠다면 그것이 막고 있던 실패가 조용한 통과로 바뀌지 않았는지 확인한다.

## 4. 보고

- 판정: 완료 / 미완료(빈 칸 목록)
  - 미완료면 빈 칸 원인으로 돌아간다: TC 가 스펙에 없음·근거 ID 없음 → `/add:spec`, 테스트·구현·Then 단언·mutation 실패 TC 가 없음 → `/add:tdd`
- 실행한 명령과 결과, 실행하지 못한 것(실기기, 다른 저장소)을 구분해 적는다.
- 대조 표는 PR 본문이나 세션 보고에만 쓰고 스펙 문서에는 남기지 않는다.
