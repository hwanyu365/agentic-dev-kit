# agentic-dev-kit — 개발 절차 (분류·변경 범위)

## 1. 개요

- 문서 정보: 작성 2026-11-20 / 기준 커밋 `df5a528` (origin/main) / 이슈 GH#75
- 기능: 변경을 chore·feat·bugfix 로 나누는 기준과, 변경 범위를 셀 때 무엇을 세는지 정한다
- 목적 (Why)
  - 문구·번역·오타만 고친 변경도 "사용자에게 보이는 동작" 이라 스펙·Red 테스트 대상이 된다 → 새 테스트는 고정할 계약 없이 문자열 사본이 된다.
  - eli5 를 생략해도 되는 변경의 기준이 PR 템플릿에 "구조 설명이 필요한 변경" 으로만 있다.
  - 변경 범위는 코드 경로만 센다 → 바뀌기 전 동작을 전제로 쓴 문서가 남고, 리뷰가 한 줄씩 지적하면 그 줄만 고쳐 같은 전제의 다른 문장이 남는다.

## 2. 목표 및 범위

- In Scope: 템플릿·adk `CLAUDE.md` 개발 절차의 chore 정의와 검증 절의 변경 범위 줄, 템플릿·adk PR 템플릿의 eli5 주석, 템플릿·adk chore 이슈 템플릿, 테스트 약화를 보는 리뷰 기준(`/adk:ship` 1·review.md·템플릿·adk `claude-review.yml`), `/adk:verify` 3, `/adk:ship` 3-4
- Out of Scope
  - eli5 페이지를 언제 만들고 어떻게 쓰는지 → GH#77
  - 이전 동작 서술을 기계로 찾는 검사 → 전제가 참인지는 문장을 읽어야 판정된다

## 3. 요구사항

- `US#1` [요구사항] 저장소 소유자로서, 문구만 고친 변경에 공수가 들지 않도록, 문자열 값만 바뀌는 변경은 스펙·새 테스트 없이 처리되기를 원한다. → FR#1, FR#2
- `US#2` [요구사항] 저장소 소유자로서, 리뷰가 낡은 문서를 한 줄씩 지적하지 않도록, 동작을 바꾼 변경이 그 동작을 전제로 쓴 서술까지 함께 고치기를 원한다. → FR#3, FR#4
- `FR#1` [요구사항] 문자열 값만 바뀌는 변경은 chore 다 (저장소 소유자 결정 2026-11-20).

  ```
  Given 변경이 화면 문구·번역·오타처럼 문자열 값만 바꾸고, 분기·조건·출력 형식·키는 그대로다
  When  /adk:spec 이 이슈를 분류한다
  Then  chore 로 분류되어 스펙·새 테스트·eli5 없이 검증 명령과 변경 범위만 확인한다
        스펙이 그 문구를 인용하면 인용만 고친다
        기존 테스트가 그 문자열을 단언하면 기대값만 새 문구로 바꾸고 PR 본문에 적는다
  ```

  - 실패 경로: 문구와 함께 키·조건·출력 형식이 바뀌거나 문구가 새로 생기면 chore 가 아니다 → 기존대로 스펙·TC 대상이다.
  - 기대값만 바꾼 단언은 약화가 아니다 → 단언하는 자리와 비교 방식이 그대로다. 단언을 지우거나 비교를 느슨하게 하면 약화다.
    - 그래서 Red 테스트 변경의 소유자 승인 대상이 아니고, 테스트 약화를 보는 리뷰 기준도 이것을 약화로 세지 않는다.
  - 변경 범위는 chore 에서도 본다 → 그 문구를 인용한 스펙과 단언한 테스트를 찾는 단계다.
- `FR#2` [요구사항] 템플릿·adk PR 템플릿의 eli5 주석은 생략해도 되는 변경을 적는다: FR#1 의 문구 변경, 포맷·의존성처럼 설명할 구조가 없는 변경.
- `FR#3` [요구사항] 변경 범위(`/adk:verify` 3, `CLAUDE.md` 검증 절)는 코드 경로에 더해 바뀐 동작을 전제로 쓴 서술을 센다.
  - 대상: 스펙·주석·README·스킬·템플릿 문서, 같은 것을 공유하는 다른 저장소의 문서
  - 판정은 낱말 일치가 아니라 그 문장의 전제가 지금 코드에서 참인지로 한다 → 같은 전제를 다른 낱말로 쓴 문장을 놓치지 않는다.
- `FR#4` [요구사항] 리뷰가 낡은 서술 하나를 지적하면 그 줄만 고치지 않고, 그 서술이 기댄 전제를 쓴 서술을 FR#3 대로 다시 센 뒤 고친다 (`/adk:ship` 3-4).
